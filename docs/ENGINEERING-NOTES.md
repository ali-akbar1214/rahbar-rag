# Engineering Notes: Architectural Questions and Failure Analyses

## 1. Indexing in API Startup: 3 Replicas and One Chroma Volume
If indexing is moved into the API startup lifecycle (e.g. FastAPI `lifespan` handler in [`api/app/main.py`](../api/app/main.py#L28-L46)), four things break immediately:
1. **Concurrent Write Lock Contention & Index Corruption**: ChromaDB persists catalog metadata in SQLite alongside HNSW binary segments on one volume. When 3 `rahbar-api` replicas boot simultaneously and invoke `store()` ([`indexer/pipeline/store.py`](../indexer/pipeline/store.py#L23-L76)), three concurrent writers race on the same collection, causing `sqlite3.OperationalError: database is locked` or torn index segments.
2. **Startup & Readiness Probe Failures (`CrashLoopBackOff`)**: Extracting, OCR-ing, and embedding 180+ pages of PDFs takes minutes—exceeding the 60-second `startupProbe` budget (`failureThreshold: 30 × periodSeconds: 2` in [`k8s/base/api-deployment.yaml`](../k8s/base/api-deployment.yaml#L70-L75)), so kubelet kills and restarts all 3 pods mid-ingestion in an endless loop while paying the full extraction/embedding cost on every restart.
3. **Every Redeploy or Pod Restart Re-indexes, and Re-indexing Requires a Redeploy**: A rolling update, HPA scale-out (3 → 8 pods), or node drain re-runs ingestion unnecessarily, and updating policy PDFs cannot happen without restarting serving pods.
4. **The Preventing Objects & Manifest Lines**:
   - The standalone batch **`Job`** ([`k8s/base/indexer-job.yaml`](../k8s/base/indexer-job.yaml#L1-L25), specifically `kind: Job` at `#L2`, `backoffLimit: 3` at `#L10`, and `restartPolicy: OnFailure` at `#L18`) plus the weekly **`CronJob`** ([`k8s/base/reindex-cronjob.yaml`](../k8s/base/reindex-cronjob.yaml#L1-L24)), which act as the sole writer.
   - The 1-replica **`StatefulSet`** for ChromaDB with `ReadWriteOnce` `volumeClaimTemplates` ([`k8s/base/chroma-statefulset.yaml`](../k8s/base/chroma-statefulset.yaml#L73-L81)) and the API's read-only `/readyz` gate checking `collection.count() > 0` ([`api/app/routes/health.py`](../api/app/routes/health.py#L80-L86)).

## 2. Readiness and Liveness Swapped, Chroma Slow for 90 Seconds
If `livenessProbe` points to `/readyz` and `readinessProbe` points to `/healthz`:
- **What happens to a 3-replica deployment**: During a 90-second Chroma slowdown, `/readyz` ([`api/app/routes/health.py`](../api/app/routes/health.py#L57-L108)) times out or returns HTTP `503`. With `periodSeconds: 10`, `timeoutSeconds: 3`, and default `failureThreshold: 3`, kubelet kills each container after ~30 seconds—well inside the 90-second slowdown. Because all 3 replicas share the same slow Chroma upstream, **all 3 pods are killed and restarted in a synchronized cluster-wide restart storm**. Meanwhile, any briefly booted pod passes `/healthz` immediately on its swapped `readinessProbe` and receives live user traffic while Chroma is still degraded, serving 500/fallback errors until killed again.
- **Why our wiring prevents it**: In [`k8s/base/api-deployment.yaml`](../k8s/base/api-deployment.yaml#L76-L90), `livenessProbe` queries `/healthz` ([`api/app/routes/health.py`](../api/app/routes/health.py#L51-L54)), which touches zero external dependencies, keeping all 3 pods alive. `readinessProbe` queries `/readyz`, which temporarily removes degraded pods from `Service/rahbar-api` endpoints without restarting a single container, then restores traffic automatically as soon as Chroma responds.

## 3. What a CPU-based HPA Measures on a Generation Service
- **What it actually measures**: While generating an answer through [`HostedProvider.generate`](../api/app/providers/llm/hosted.py#L96-L125) or [`OllamaProvider.generate`](../api/app/providers/llm/ollama.py#L62-L89), the API worker spends >90% of wall-clock latency blocked on network socket I/O waiting for upstream LLM tokens (`httpx.Client.post`). During I/O wait, container CPU usage stays near idle—our [`k8s/base/hpa.yaml`](../k8s/base/hpa.yaml#L1-L22) reports only `18%/70%` (`18m` of `100m` request in [`docs/evidence/05-kubectl-get-hpa.txt`](evidence/05-kubectl-get-hpa.txt#L3)). Thus, a CPU-based HPA only measures JSON serialization, prompt string formatting, and ASGI event-loop overhead—not LLM saturation.
- **Which signal should scale this service**: **Concurrent in-flight `/api/ask` requests per pod** (or upstream generation queue depth / p95 `/api/ask` latency).
- **What we would build to use it**: Export an `rahbar_in_flight_requests` Prometheus `Gauge` incremented/decremented inside `request_context` middleware ([`api/app/main.py`](../api/app/main.py#L51-L72)), deploy Prometheus + `prometheus-adapter` (or KEDA `ScaledObject`) exposing `custom.metrics.k8s.io`, and add a `Pods` metric target (e.g., `averageValue: "10"` concurrent requests per pod) in [`k8s/base/hpa.yaml`](../k8s/base/hpa.yaml#L16-L22).

## 4. Indexer Peak Memory, Limits, Margin, and Exit Code
- **Peak Memory**: Measured via `kubectl top pods -n rahbar` ([`docs/evidence/03-kubectl-top.txt`](evidence/03-kubectl-top.txt#L9)), `rahbar-indexer-job` peaks at **`680Mi`** during PDF page rasterization (`pdf2image` / `pytesseract` in [`indexer/pipeline/extract.py`](../indexer/pipeline/extract.py#L85-L98)) and 32-chunk embedding batches ([`indexer/pipeline/embed.py`](../indexer/pipeline/embed.py#L35-L85)).
- **Configured Request & Limit**: `requests.memory: 512Mi` and `limits.memory: 2048Mi` (`2Gi`) in [`k8s/base/indexer-job.yaml`](../k8s/base/indexer-job.yaml#L41-L47) (matched identically in [`k8s/base/reindex-cronjob.yaml`](../k8s/base/reindex-cronjob.yaml#L44-L50)).
- **Margin**: `2048Mi - 680Mi = 1368Mi` headroom (**`3.01x`** peak usage), absorbing multi-page 300-DPI scanned PDF buffers without starving the 6 GiB Minikube node.
- **Wrong-Limit Exit Code**: Setting `limits.memory` below `680Mi` (e.g., `512Mi`) triggers the Linux kernel cgroup OOM killer (`SIGKILL`, signal `9`), terminating the container with **Exit Code `137`** (`128 + 9`, `Reason: OOMKilled`).

## 5. `recall@5` by Question Type: Where It Is Worst and Why
- **Worst Category**: `exact` (`0.8000` in [`eval/results.json`](../eval/results.json#L9)), trailing `ordinary` (`1.0000` at `#L7`) and `version` (`1.0000` at `#L8`), with overall `recall@5 = 0.9333`.
- **Why Dense Embeddings Struggle**: Bi-encoder dense models (`nomic-embed-text`, 768 dims) compress whole-chunk semantics into a single continuous vector. They excel at conceptual synonymy (`ordinary` questions), but smooth over rare lexical identifiers—clause numbers (`1.21`, `5.6`, `3.12` in [`eval/golden.yaml`](../eval/golden.yaml#L75-L108)), course codes (`CS4032`), and exact PKR fee numerals (`12,000`)—mapping distinct numbers or phrases like `"five-year limit"` (`q15`, clause `3.12` credit transfer) into overlapping degree-duration neighborhood regions.
- **RAG Lecture Technique That Addresses It**: **Hybrid Retrieval (Sparse BM25 + Dense Vector Search) combined with Reciprocal Rank Fusion (RRF)**, optionally followed by a cross-encoder reranker, so exact token/clause hits receive high lexical rank alongside semantic matches.

## 6. `EMBED_MODEL` Changed on API Only: Guardrail Action
- **What our system does**: When `EMBED_MODEL` is changed in [`k8s/base/configmap.yaml`](../k8s/base/configmap.yaml#L9) and only `Deployment/rahbar-api` restarts:
  1. On boot, `lifespan` calls `verify_embedding_pin` ([`api/app/main.py`](../api/app/main.py#L38), [`api/app/routes/health.py`](../api/app/routes/health.py#L19-L48)) and immediately logs `startup embedding pin conflict`.
  2. Every `/readyz` probe ([`api/app/routes/health.py`](../api/app/routes/health.py#L89-L105)) compares `collection.metadata["embed_model"]` (written by [`indexer/pipeline/store.py`](../indexer/pipeline/store.py#L37-L43)) against `settings.embed_model`, logs the conflict, and returns **HTTP `503`**.
  3. Because `maxUnavailable: 0` is set ([`k8s/base/api-deployment.yaml`](../k8s/base/api-deployment.yaml#L14-L15)), the new pod sits at `0/1 READY` ([`docs/evidence/06-rollout-and-embedding-pin.txt`](evidence/06-rollout-and-embedding-pin.txt#L12)), Kubernetes withholds it from `Service/rahbar-api`, and the 3 healthy pods keep serving traffic with zero user impact.
- **What would happen without the guardrail**: If dimensions differ, Chroma raises runtime query errors (500/fallback); worse, if both models output 768 dimensions, Chroma computes cosine similarity between incompatible vector spaces **with no error anywhere**, returning random chunks or causing false abstentions across every question.

## 7. The Failure That Cost More Than an Hour
- **Symptoms**: Right after applying our default-deny `NetworkPolicy` ([`k8s/base/networkpolicy.yaml`](../k8s/base/networkpolicy.yaml#L1-L10)), all `rahbar-api` pods stayed `0/1 READY` and `/readyz` failed with `socket.gaierror: [Errno -3] Temporary failure in name resolution` when connecting to `rahbar-chroma` and `rahbar-redis`.
- **What we wrongly believed first**: We assumed Minikube's `CoreDNS` pods or Calico's vxlan overlay had crashed, and spent nearly an hour restarting `coredns` in `kube-system`, recreating the `rahbar-chroma` Service, and inspecting `/etc/resolv.conf`.
- **The command & output that told the truth**: Inspecting `kubectl describe networkpolicy default-deny-all -n rahbar` (`Policy Types: Ingress, Egress`) alongside:
  ```bash
  kubectl logs -l app=rahbar,component=api -n rahbar | grep -F "unreachable"
  ```
  and testing UDP/53 from a debug pod showed `default-deny-all` blocked **all** pod egress—including DNS lookups to `kube-dns` (`kube-system:53`). Adding `allow-dns-egress` on UDP/TCP port `53` ([`k8s/base/networkpolicy.yaml`](../k8s/base/networkpolicy.yaml#L12-L30)) resolved service names immediately and brought all 3 API replicas to `1/1 READY`.
